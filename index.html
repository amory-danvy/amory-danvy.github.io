/ 01 — projet personnel

Générateur de CV Dynamique

// contexte

Projet personnel réalisé pendant le BTS SIO SLAM. Il figure dans mon tableau de synthèse comme projet d'apprentissage, mais ce n'est pas l'un des deux projets que je présente à l'épreuve E6 (ces deux-là sont Patrimonia et Vintgen).

Point de départ : faire un CV propre sur Canva est pénible. L'alignement, le moindre changement de poste qui décale tout. Je voulais un outil où je remplis mes données une fois, et la mise en page se fait toute seule.

// ce que ça fait

Application web qui permet de créer un compte, saisir ses informations dans un formulaire (état civil, expériences, formation, compétences), choisir un thème (Standard, Blue, Dark) et exporter le CV en PDF.

// stack & choix

  • Python (Flask) côté serveur — minimal à apprendre, suffisant pour un CRUD avec auth.
  • HTML / CSS pour les templates de CV — un template par thème, contenu injecté côté serveur.
  • SQLite pour stocker les comptes utilisateurs et leurs données — pas besoin d'un PostgreSQL pour ce volume.
  • WeasyPrint pour transformer le HTML rendu en PDF (alternative à pdfkit, meilleure gestion du CSS print).

// difficulté principale

Gérer la pagination du PDF quand le contenu déborde d'une page. Il a fallu adapter le CSS print pour que les sections (expériences, formations) ne se coupent pas au milieu d'un bloc.

// statut

Code en ligne sur GitHub. Projet considéré comme abouti pour ce que j'avais à apprendre dessus, je n'y reviens plus depuis.

// compétences slam mobilisées

  • Concevoir et développer une solution applicative
  • Gérer les données (modélisation utilisateur + données CV)
  • Sécuriser l'accès (authentification + hash des mots de passe)

/ 02 — projet bts · épreuve e6

Patrimonia

// contexte

L'un des deux projets que je présente à l'épreuve E6 du BTS SIO SLAM. Cas d'usage choisi parce qu'il oblige à toucher tous les étages d'une application métier : authentification, modèle de données dans le temps, calculs (simulateur d'intérêts), restitution graphique.

Domaine retenu : le suivi de patrimoine (actifs, valorisations successives, simulation d'intérêts). Lisible visuellement, parlant côté jury, et assez riche pour justifier une vraie modélisation.

// ce que ça fait

Application full-stack avec authentification, dashboard interactif (liste d'actifs + graphiques d'évolution), simulateur d'intérêts simple/composé, et historique des valorisations.

// stack & choix

  • React côté front — composants, hooks, gestion d'état, le standard que je voulais maîtriser.
  • Node.js + Express côté back — API REST classique, plus instructif qu'un framework "tout-en-un".
  • SQLite pour la persistance — base légère, pas besoin de PostgreSQL pour prototyper.
  • Tailwind CSS — styling rapide pour un projet où l'esthétique n'est pas le point central.

// difficulté principale

Modélisation des données : un actif a un historique de valorisations dans le temps, et le simulateur d'intérêts doit gérer plusieurs modes de calcul (simple, composé). Trouver le bon schéma sans sur-ingénieurer pour un prototype a demandé plusieurs itérations.

// statut

Code en ligne sur GitHub. Couvre les fonctionnalités cibles, n'est pas déployé en production (pas l'objectif).

// compétences slam mobilisées

  • Concevoir et développer une solution applicative full-stack
  • Gérer les données (modélisation relationnelle, requêtes)
  • Sécuriser (authentification, contrôle d'accès aux ressources)

/ 03 — projet alternance · siccardi tech leads

NewsHunter — Tweet Fetcher

// contexte

Projet réalisé dans le cadre de mon alternance chez Siccardi Tech Leads. L'équipe avait besoin d'un outil pour suivre l'actualité IA et dev sans devoir scroller Twitter/X manuellement chaque matin.

Le repo s'appelle NewsHunter2 parce que c'est la deuxième itération : j'ai refait l'architecture après avoir buté sur les limites de la première version.

// ce que ça fait

Script Python qui interroge l'API X via Tweepy à intervalle régulier, filtre les tweets selon des mots-clés et des comptes suivis, et archive le résultat dans un fichier JSON horodaté.

// stack & choix

  • Python — langage de prédilection pour scripter ce genre d'automatisation.
  • Tweepy plutôt que des requêtes brutes vers l'API X — gère l'auth OAuth, la pagination et les rate limits proprement.
  • JSON pour l'archivage — lisible humainement, pas besoin de SGBD pour un volume modeste.
  • Task Scheduler Windows pour planifier l'exécution.

// difficulté principale

Le rate limiting de l'API X — la version gratuite donne très peu de requêtes par mois. J'ai dû filtrer plus en amont (moins de mots-clés, fréquence réduite) plutôt que de tirer plus de données et trier après.

// pourquoi une v2

La V1 fonctionnait mais était monolithique : un gros script qui faisait tout. Pour la V2, j'ai séparé les responsabilités (config / fetch / filtrage / stockage) pour pouvoir modifier un bloc sans casser les autres.

// statut

Code en ligne sur GitHub. Tourne ponctuellement quand j'en ai besoin pour ma veille.

// compétences slam mobilisées

  • Concevoir et développer une solution applicative (refactor V1 → V2)
  • Gérer les données (archivage structuré des tweets)
  • Travailler en mode projet (itération, identification des limites de la V1)

/ 04 — projet bts · épreuve e6

Vintgen — IA & automatisation

// contexte

L'autre des deux projets que je présente à l'épreuve E6 du BTS SIO SLAM, avec Patrimonia. Cas d'usage concret : un vendeur sur Vinted passe beaucoup de temps à rédiger une annonce (titre, description, prix conseillé, hashtags). Je voulais voir si une IA multimodale pouvait raccourcir ce processus à 10 secondes : photo → annonce complète.

// ce que ça fait

Application web mobile-first. L'utilisateur upload une photo d'un article, Vintgen interroge un modèle de vision (Gemini Vision) avec un prompt structuré, parse la réponse et affiche : titre suggéré, description optimisée, prix conseillé, et hashtags. L'utilisateur peut éditer et copier le résultat.

// stack & choix

  • Next.js + TypeScript — full-stack moderne, types stricts pour limiter les bugs au runtime, API routes côté serveur.
  • Tailwind CSS — styling rapide, classes utilitaires, pas de context-switching CSS / HTML.
  • Gemini Vision (Google) plutôt que GPT-4 Vision — quotas plus généreux côté gratuit, API mieux documentée pour les usages multimodaux.
  • Convex comme backend temps réel — historique des annonces générées par utilisateur, schéma typé partagé entre client et serveur, pas de serveur Express à maintenir.
  • PWA — l'utilisateur installe l'outil comme une app native sur son téléphone et prend la photo direct, sans upload de fichier.

// difficulté principale

Faire en sorte que la sortie du LLM soit fiable et parsable. Gemini Vision peut retourner du texte libre formaté différemment d'une fois à l'autre. J'ai construit un prompt très structuré (format JSON imposé en sortie) et ajouté un parser tolérant aux petites variations de syntaxe.

// statut

Code récemment passé en public sur GitHub. C'est le projet le plus avancé techniquement de mon portfolio.

// compétences slam mobilisées

  • Concevoir et développer une solution applicative full-stack moderne
  • Gérer les données (schéma Convex pour l'historique utilisateur)
  • Sécuriser (clés API IA stockées côté serveur, jamais exposées au client)
  • Intégrer un service tiers (API Gemini Vision)
